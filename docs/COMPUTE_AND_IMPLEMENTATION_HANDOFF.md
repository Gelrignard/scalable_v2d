## 1. Decisions and scope

We must run the participant-side pipeline ourselves. The leaderboard scores uploaded results; it does not train our policies after receiving source code.

The [official FAQ](https://nvidia-isaac.github.io/video_to_data/v2d_challenge/assets/v2d_challenge_2026_faqs.pdf) requires learned-policy object trajectories covering all 30 references per tier, whole-body control, and reproducibility metadata. Pretrained controllers are allowed. Checkpoint files are retained for validation; their hashes accompany results.

The [challenge page](https://nvidia-isaac.github.io/video_to_data/v2d_challenge/) requires separate submissions for the three equally weighted tiers. Its deadline is **4 November 2026, 5 p.m. EST**, 18 calendar days after this note. Code release and a technical report are also relevant to award eligibility.

The current [submission kit](https://nvidia-isaac.github.io/video_to_data/v2d_challenge/assets/v2d_submission_kit.zip) directs participants to supply one checkpoint per scored episode through an episode-to-checkpoint map. Budget 30 episode-level training jobs per tier, or 90 for all tiers, for the standard workflow. This is a job-count assumption, not a claim that every checkpoint must have a different network architecture.

Research comparisons are additional work. We do not need to run every ablation over all 90 cases before learning whether the idea is useful.

## 2. Tier 3: reconstruct motion; determine the mesh-input condition separately

Tier 3 needs an estimated human/object interaction from the released monocular third-person video. It is not sufficient to reconstruct only the object's shape. We need human body/hand motion and object poses over time, with usable scale and a consistent coordinate frame.

The current [Track 2 release README](https://huggingface.co/datasets/nvidia/video_to_data_challenge/blob/main/track_2/README.md) still describes Tier 1 and Tier 2 pose exports; Tier 3 reconstructions must be generated by the participant. The 30 sequences share a 22,990-frame timeline. At 30 Hz this is about 12.8 minutes of video; short input duration does not imply real-time reconstruction.

The current V2D implementation is [CARI4D MHR](https://github.com/nvidia-isaac/video_to_data/blob/main/reconstruction/modules/v2d_cari4d/README.md). Its input contract is RGB video, human/object masks, and a textured object mesh. It estimates depth, human motion, object motion, and refined interaction. The mesh is an input, not an output of its main inference command.

This creates two distinct budget cases:

| Condition | Work before CARI4D |
|---|---|
| A suitable provided mesh is permitted for the Tier 3 input condition | Prepare masks and use that mesh |
| A new mesh is needed or required | Prepare masks, generate a mesh from video imagery, establish metric scale, then run CARI4D |

The kit uses the released mesh for **scoring** Tier 3. That does not by itself settle whether using a clean Tier 1 mesh to initialize Tier 3 reconstruction is permitted. I did not find an explicit Tier 3 mesh-input permission statement in the inspected rules. Confirm that condition before choosing the production route. Do not silently substitute clean human/object trajectories.

For an early integration test, a provided-mesh run can be labeled as such, without treating it as a verified Tier 3 competition result.

### Choose one CARI4D implementation

The original [NVlabs/CARI4D custom-video workflow](https://github.com/NVlabs/CARI4D/blob/main/docs/custom_video.md) and V2D's MHR implementation have different dependencies, human representations, and preprocessing. Do not combine their scripts by matching names alone.

Prefer the V2D MHR workflow initially because it is the challenge-associated integration. Its source includes stage caching and timing. Use pretrained inference; training the reconstruction models from scratch is outside this project.

The original repository's statement that SAM3 mask processing can fit 24 GB using 300-frame chunks is evidence for **that segmentation stage only**, not a 24 GB guarantee for the complete MHR pipeline.

### Tier 3 implementation deliverables

1. A manifest per episode containing video identity, frame IDs/timestamps, mesh identity, model versions, coordinate conventions, and reconstruction configuration.
2. Human/object masks with the correct frame count and image dimensions.
3. Human reconstruction parameters and metric joints, plus object SE(3), visibility/confidence, and geometry.
4. An explicit adapter from the selected reconstruction representation to the input expected by our retargeter. Do not assume MHR parameters can simply be renamed to SOMA-X columns.
5. A fixed, documented mapping into the released Track 2 world frame and object body frame, using permitted information.
6. Recorded per-stage wall time, peak GPU memory, host RAM, disk usage, and failures.

**Coordinate alignment is an unresolved integration requirement.** The released exports do not provide general camera calibration alongside the pose columns. The submission packer requires the custom input reference in the released world frame. Establish how this transform is obtained without fitting to clean object trajectories. If the permitted calibration route is unclear, obtain an organizer clarification before producing the full Tier 3 batch.

## 3. Is a 24 GB RTX 4090 suitable?

The [RTX 4090 specification](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4090/) lists 24 GB VRAM. It is a reasonable candidate for a **bounded feasibility/profile run**, but we have not established that all default configurations fit.

| Workload | What is verified | What the implementation agent must measure |
|---|---|---|
| Mask/depth/body initialization | Stage-wise batching controls exist | Peak memory and time at the chosen resolution |
| Object tracking and CARI4D refinement | Pretrained workflow exists; commercial model card validates A100 | Full-clip memory, throughput, stability on 4090 |
| Optional mesh generation | Separate workflow, if needed | Model-specific peak memory and scale quality |
| G1 full-recipe FlashCHORD training | Documentation validates 48 GiB, with at least 46,000 MiB free | Reduced-configuration fit and learning behavior |
| Official trajectory export | Kit batch example defaults to one evaluation world | Runtime, export compatibility, provenance |
| Packing/scoring preflight | CPU-side scripts | All required rows and frame transforms |

The [CARI4D commercial model card](https://huggingface.co/nvidia/cari4d_commercial/blob/main/README.md) validates A100 and calls for separate validation on other targets. It does not establish a minimum VRAM figure for our videos.

The [FlashCHORD requirements](https://github.com/nvidia-isaac/video_to_data/blob/main/robotic_grounding/flash_chord/README.md) concern its full training setup. Replay and viewing are lighter. A 4090 does not meet that documented full-training memory specification; a modified recipe needs its own validation.

Consequently, “CV uses more memory, RL uses more hours” is not a dependable rule. CV has expensive model/refinement stages, while RL can hold a large simulation batch and replay buffer continuously. Either can be the memory bottleneck. Repeating RL across tiers, episodes, seeds, and ablations is likely to dominate aggregate hours, but we must measure both.

### CARI4D memory controls

The [V2D inference launcher](https://github.com/nvidia-isaac/video_to_data/blob/main/reconstruction/modules/v2d_cari4d/docker/run_inference.py) exposes, among others:

| Parameter | Inspected default |
|---|---:|
| moge_batch_size | 8 |
| sam3d_chunk_size | 16 |
| sam3d_refit_batch_size | 512 |
| coconet_render_batch_size | 32 |
| postopt_num_steps | 300 |
| postopt_batch_size | 0 |
| render_batch_size | 4 |

The [refinement implementation](https://github.com/nvidia-isaac/video_to_data/blob/main/reconstruction/modules/v2d_cari4d/lib/cari4d/learning/training/mhr_opt_refineout.py) interprets zero post-optimization batch size as the full clip. Positive values select temporal windows. Reducing inference batches and reducing refinement windows are different changes: windowed refinement changes which frames contribute to an update and needs quality checks. Do not assume unchanged output quality merely because it avoids an out-of-memory error.

Run stages sequentially and cache outputs, instead of keeping all vision models resident. Verify peak memory on the longest sequence as well as a short test. A short-prefix success can miss full-clip allocations.

### RL memory controls

The [G1 FlashSAC recipe](https://github.com/nvidia-isaac/video_to_data/blob/main/robotic_grounding/flash_chord/src/flash_chord/configs/experiment/g1_recon_body_flash_sac.yaml) uses 2,048 simulation worlds, a ten-million-transition replay buffer, float16 observation storage, and approximately 350 million environment transitions.

Its [replay allocator](https://github.com/nvidia-isaac/video_to_data/blob/main/robotic_grounding/flash_chord/src/flash_chord/training/flash_sac/replay.py) provides an allocation-free logical memory calculation. For observation dimension \(d_o\), action dimension \(d_a\), objective-term count \(d_r\), critic-context dimension \(d_c\), observation bytes \(b_o\), and capacity \(B\), its main ring payload is

$$
M_{\rm ring}
=B\left[2d_ob_o+4(d_a+d_r+2d_c)+2\right]\ {\rm bytes}.
$$

This excludes simulation memory, networks/optimizers, sampled batches, compilation workspaces, and allocator overhead. Query actual dimensions; do not insert guessed dimensions and call the result a measured requirement.

Start with one environment for physical replay/export. For a reduced training feasibility experiment, explore a bounded sequence such as 128, 256, then 512 worlds, and a 0.5–1 million transition buffer. These are **candidate settings**, not a validated learning recipe. Keep replay minimum size, minibatch size, curriculum scheduling, and update-to-data ratio internally consistent.

Use the same chosen settings for baseline and corrected references. Lowering the corrected run's buffer while leaving the baseline at ten million entries would confound the comparison.

A useful operational target is under roughly 20–21 GiB peak on a dedicated 24 GB GPU, leaving working headroom; this is our planning margin, not an official requirement. Training, evaluation, and CV should not run concurrently on that GPU during profiling.

### Host resources

The quoted 16 CPU cores and 120 GB host RAM are a promising starting allocation. The **30 GB disk allowance is the main capacity concern**. It is not a safe planning allowance for the combined containers, vision weights, robot assets, and reconstruction intermediates. It might be workable for a tightly scoped run if preinstalled framework/container layers and external model caches do not count against it; establish the provider's accounting before renting for setup.

I would provision approximately 300–500 GB of persistent working storage for comfortable combined development, then shrink that allocation if a manifest and one-episode measurement justify it. This is a practical allocation, not a measured minimum. Keep temporary per-episode artifacts bounded and share immutable weights across runs.

“CUDA up to 13.2” does not identify the installed NVIDIA driver or prove that Docker GPU/EGL access works. Check the actual driver against the selected container and FlashCHORD's documented 580+ requirement. Different reconstruction stages can use their own CUDA/PyTorch environments; do not upgrade every dependency to CUDA 13.2 indiscriminately.

Disk and RAM deserve attention: retaining 22,990 frames at an illustrative 608×1080 resolution as raw uint8 RGB plus float32 depth alone occupies about 106 GB, before masks, meshes, checkpoints, containers, and duplicated intermediates. Actual released dimensions and compressed sizes must be inventoried. Process/cache by episode instead of assuming everything fits in RAM.

Keep weights, compiled caches, outputs, and checkpoints on persistent storage. Separate downloading/building from GPU profiling wherever the provider permits it. Include any billed idle/setup time and storage charges in monetary cost.

## 4. Quantitative budget: measured facts versus scenarios

The [CHORD paper](https://arxiv.org/html/2607.00033v2) reports approximately two hours per sequence on an L40S for its reported FlashSAC setup. This is a useful reference, not a timing guarantee for whole-body G1 on a 4090. It also reports evaluation on 1,831 tasks; our pitch should target lower cost per successful policy rather than assert that CHORD has no large-scale experiments.

### Policy-training sensitivity

Let \(h\) be measured rental GPU-hours for one episode-level training job. The following assumes one selected training seed per final episode and no reuse of earlier jobs:

| Work | Jobs | If \(h=2\) h | If \(h=4\) h | If \(h=8\) h |
|---|---:|---:|---:|---:|
| One tier | 30 | 60 h | 120 h | 240 h |
| Tier 1 and Tier 2 | 60 | 120 h | 240 h | 480 h |
| All three tiers | 90 | 180 h | 360 h | 720 h |
| Initial pilot: 1 episode × 2 tiers × 2 methods × 1 seed | 4 | 8 h | 16 h | 32 h |
| Small paired study: 2 episodes × 2 tiers × 2 methods × 2 seeds | 16 | 32 h | 64 h | 128 h |
| Three-way study: 3 episodes × 2 tiers × 3 methods × 3 seeds | 54 | 108 h | 216 h | 432 h |

These are arithmetic scenarios, not predicted runtimes. Reusable corrected-policy runs can count toward the final submission; do not double-count them. Failed training, method tuning, reconstruction, and evaluation are excluded from this table.

|---|---:|---:|---:|
| One tier | $19.20 | $38.40 | $76.80 |

| Effective throughput | Training-loop time |
|---|---:|
| 5,000 transitions/s | 19.44 h |
| 20,000 transitions/s | 4.86 h |
| 50,000 transitions/s | 1.94 h |

Add startup, compilation, evaluation, and recovery time. This estimates time to a step budget, **not time to successful learning**. Our method's claim depends on reaching a quality threshold earlier.

### Reconstruction sensitivity

Let \(c\) be hours per complete Tier 3 clip, after caches are prepared. If \(c\) is 0.25, 1, or 3 hours, the 30 clips require 7.5, 30, or 90 GPU-hours respectively. These are deliberately labeled scenarios because no complete 4090 measurement is available.

At $0.32/hour, these reconstruction scenarios cost $2.40, $9.60, or $28.80 respectively, excluding storage and setup.

Record optional mesh generation separately. Cached Tier 3 reconstruction is reused across correction variants and RL seeds; it should not be rerun for every policy experiment.

### Total money and time

For hourly rental rate \(r\),

$$
\text{cost}
=r\left(H_{\rm setup}+H_{\rm CV}+H_{\rm training}
+H_{\rm evaluation}+H_{\rm failed\ attempts}\right)
+\text{storage/transfer charges}.
$$

As a **worked planning example**, 90 jobs at 4 h each, 30 h reconstruction, and 10 h setup/evaluation total 400 h. A chosen 20% contingency brings that to 480 h, or **$153.60** at the user's rate, plus storage/transfer charges. These overhead and contingency choices are planning allowances, not measured runtime predictions.

One continuously available GPU has at most 432 hours in an 18-day window. Thus, that example already exceeds the remaining calendar window, before considering human development time. At 2 h per policy, the same assumptions give 264 h including contingency, costing **$84.48**. This is why early measurement and a bounded research pilot matter.

The first rental allocation should be only **2–4 hours of prepared profiling**, with explicit stop conditions: **$0.64–$1.28** in GPU rental at the quoted rate. This allocation buys information about fit and throughput, not a promise of converged policies. Resolve storage and weight access first. Do not precommit to a full 90-job run before observing it.

## 5. Policy integration and experiment requirements

### Existing inputs

The available book artifacts are:

- [Original reference](../correction/outputs/tier1_book/retargeted/contact_aware.npz)
- [Corrected reference](../correction/outputs/tier1_book/dynamics_guided.npz)
- [Physical-assumption and FK audit](../correction/outputs/tier1_book/fk_force_audit.json)

Both references contain q [900,50], timestamps [900], object_positions [900,3], object_wxyz [900,4], contact fields, and metadata_json. They are **our reference format**, not directly the FlashCHORD motion format, a policy, or an evaluator trajectory.

The book correction changes only a short phase, has unresolved sticking, and has not passed physical rollout. Use it for adapter/debug work first. It cannot support a claim of full-episode feasibility or a strong full-episode learning result.

The trainer agent must:

1. Read joint ordering and floating-base conventions from metadata/model code; never map joints by array position without checking names.
2. Export a compatible G1 motion_v1/single_robot reference with correct robot/object assets, contacts, timing, and support surfaces.
3. Match simulator mass, inertia, friction, geometry, action semantics, and controller gains to the correction inputs.
4. Use a permitted whole-body controller, such as the provided SONIC integration, and validate unassisted physical playback.
5. Preserve original input object motion for scoring purposes; distinguish policy reference, simulated state, and evaluator reference.
6. Export genuine learned-policy rollouts. No object teleportation or residual virtual object assistance in the final unassisted evaluation.

### Fair efficiency comparison

The primary comparison on both Tier 1 and Tier 2 is original versus corrected references under identical trainer settings and paired seeds. Add geometry-only repair to determine whether the force-based component provides value beyond contact closure.

Log aggregate environment transitions, gradient updates, wall seconds, GPU model/peak VRAM, checkpoints, and official tracking metrics at consistent intervals. “Fewer iterations” is insufficient if the number of parallel environments or updates per iteration differs.

Define the success threshold before comparing runs. Report runs that never reach it within budget as failures/censored runs. Report both learning steps and total cost, including offline correction.

For Tier 2, improved tracking of a noisy input is not automatically improved tracking of the clean evaluation target. Use the official scoring pipeline for comparisons, while keeping clean trajectories out of reconstruction, retargeting, correction, and training. Do not initialize a Tier 2/3 task policy from the same episode's clean Tier 1 trained policy. Generic pretrained controllers are a different case.

Keep the research robustness evaluation separate from the fixed official submission protocol. Extra random initial conditions/seeds are useful research tests; they do not replace the required submission rollout.

The [Track 2 kit guide](https://nvidia-isaac.github.io/video_to_data/v2d_challenge/assets/v2d_submission_kit.zip) gives this sequence:

1. Evaluate each episode's checkpoint to an episode_XXXXXX.parquet rollout.
2. Pack those rollouts into one CSV for the selected tier.
3. Validate complete required episode/frame/object rows.
4. Submit the same CSV to the tier's four metric competitions.

The [example evaluation runner](https://nvidia-isaac.github.io/video_to_data/v2d_challenge/assets/v2d_submission_kit.zip) defaults to world-count 1 with explicit resets. Do not budget 4,096 evaluation worlds merely because a generic evaluator uses that default.

For a custom Tier 3 input, the packer accepts a frame-reference directory. Its NPZ interface requires episode_index, coordinate_frame = released_track2_world, frame_index [T], and pose_xyzw [T,1,7]. This is **xyzw**, whereas our saved object quaternions are **wxyz**. Provide the actual policy-input trajectory in the released frame, not the clean target.

The packer handles a fixed rigid conversion between the evaluation reference and the selected tier input. Do not replace it with per-frame alignment or a clean-reference fit, which would hide reconstruction/tracking error.

Retain checkpoint hashes, evaluator/packing code hashes, configuration, and the accessible GitHub commit used. Verify compatibility with the current toolkit at submission time; do not bypass provenance checks.

A one-episode export/packing dry run should be completed early for integration, followed by full-coverage preflight before an actual submission. A one-episode pilot is not a valid all-30 result.

## 8. What is not required for this project

We do not need to train the vision foundation models, build a VLA, fine-tune GR00T, or perform real-robot deployment to test this Track 2 contribution. Those are downstream possibilities, not part of the current compute budget.

The work outside our correction is nevertheless substantial: reconstruction/adaptation for Tier 3, scene/controller integration, policy training, physical evaluation, submission formatting, and reproducibility.
